# Архитектура: слоевой пайплайн (build-time данные → runtime презентация)

## Обзор

Проект — не веб-приложение и не сервис, а **двухстадийный слоевой пайплайн**:
офлайн-слой данных (Python/pandas) предвычисляет агрегаты и выгружает слим-JSON,
а слой презентации (один self-contained `index.html`) потребляет **только** этот
готовый JSON, встроенный инлайн. Стадии разделены жёсткой однонаправленной
зависимостью: презентация зависит от контракта данных (`SPEC.md` §2), но никогда —
от сырых данных или рантайм-загрузки.

Это простейший подходящий паттерн (Layered) — минимальное разделение ответственности
без формализма DDD/портов, которого тут не требуется: домен софта тривиален, деплой
единичен (один HTML-файл), команда мала.

## Обоснование решения

- **Тип проекта:** single-file HTML scrollytelling + офлайн-пайплайн данных
- **Стек:** Python + pandas (build-time); HTML/JS + d3 (runtime)
- **Ключевой фактор:** конституция `SPEC.md` §0 — «один self-contained файл» и
  «агрегация офлайн, браузер потребляет только производное». Архитектура обязана
  физически разделить вычисление данных и их показ, с барьером против рантайм-fetch.
- **Матрица:** team 1, domain complexity Low, single deployment → **Layered**.

## Структура папок

```text
insba_dashboard_contest/
├── SPEC.md                      # Источник истины (контракт данных §2 — граница слоёв)
├── RULES.md                     # Enforceable-аксиомы (read-only гейт)
├── index.html                   # ── СЛОЙ ПРЕЗЕНТАЦИИ (runtime) ──
│                                #    один JS-блок + <script id="seed-data">
├── pipeline/                    # ── СЛОЙ ДАННЫХ (build-time, Python) ──
│   ├── fetch.py                 #    скачивание/чтение датасета Kaggle
│   ├── aggregate.py             #    дельта-метод, per-36, survival, skill_decline, notable
│   ├── schema.py                #    контракт §2: валидация формы и бюджета < 300 КБ
│   ├── build.py                 #    оркестратор: fetch → aggregate → validate → emit JSON
│   └── tests/                   #    pytest — пишутся РАНЬШЕ реализации (TDD)
│       ├── test_delta_method.py
│       ├── test_per36.py
│       ├── test_survivorship.py
│       └── test_schema_budget.py
├── data/                        # (gitignore) сырьё и промежуточные файлы пайплайна
│   └── aging.json               # производный слим-JSON (вход для встраивания в HTML)
└── .ai-factory/                 # контекст AI Factory
```

> Структура расширяет фактическое состояние проекта (сейчас есть только `SPEC.md`,
> `RULES.md`, `PROMPT.md`), а не заменяет его. `index.html` и `pipeline/` создаются
> в Фазах 2 и 1 соответственно.

## Правила зависимостей

Поток строго однонаправленный, через границу-контракт `SPEC.md` §2:

```text
[Источник данных] → fetch → aggregate → schema(валидация) → слим-JSON → index.html
```

- ✅ `index.html` потребляет встроенный слим-JSON (производное по контракту §2).
- ✅ `pipeline/` зависит от датасета-источника и от схемы контракта.
- ✅ Внутри пайплайна: `build` → (`fetch`, `aggregate`, `schema`); модули агрегации
  не импортируют оркестратор.
- ❌ `index.html` не делает `fetch` к источникам/эндпоинтам в рантайме (см. `RULES.md`).
- ❌ Презентация не содержит логику агрегации — только показ готовых рядов.
- ❌ Пайплайн ничего не знает про DOM/верстку — он отдаёт данные, не представление.

## Коммуникация между слоями

- **Единственный контакт слоёв — контракт данных `SPEC.md` §2** (player-season +
  агрегаты `aging_curve` / `survival` / `skill_decline` / `notable`). Меняется контракт —
  меняются обе стороны осознанно, с бампом версии и ревью нарратива.
- **Передача — файл, не вызов:** пайплайн пишет JSON; сборка встраивает его в HTML как
  `<script id="seed-data" type="application/json">`. Никаких рантайм-каналов.
- **Обновление данных = пересборка офлайн-пайплайном**, а не подгрузка в браузере.

## Ключевые принципы

1. **Барьер рантайм-загрузки.** Финальный `index.html` самодостаточен; в нём нет сетевых
   запросов за данными. Это инвариант, проверяемый `/aif-verify` против `RULES.md`.
2. **Тонкая презентация.** JS-слой только рендерит/интерактив; вся «правда» о цифрах —
   из пайплайна. Если в JS появляется пересчёт агрегатов — это утечка слоя данных.
3. **Достоверность — на стороне данных.** Дельта-метод, per-36/per-100, контроль
   survivorship bias, доверительные коридоры и `n` вычисляются в пайплайне и покрыты
   тестами; фронт их только отображает (включая оговорки/аннотации).
4. **TDD как граница фаз.** Фаза 2 (HTML) не начинается, пока тесты пайплайна не зелёные.
5. **Бюджет как ограничение слоя данных.** Производный JSON < 300 КБ — ответственность
   `schema.py`, не фронта.

## Примеры кода

### Контракт как граница слоёв (Python, валидация в слое данных)

```python
# pipeline/schema.py — единственная «истина формы» для обеих сторон (SPEC.md §2)
REQUIRED_AGING_KEYS = {"age", "position_group", "era_bucket", "metric",
                       "value", "ci_low", "ci_high", "n"}
SIZE_BUDGET_BYTES = 300_000

def validate_payload(payload: dict, raw_json: str) -> None:
    for row in payload["aging_curve"]:
        missing = REQUIRED_AGING_KEYS - row.keys()
        if missing:                                   # падаем явно, не «тихо роняем»
            raise SchemaError(f"aging_curve: отсутствуют ключи {missing}")
    if len(raw_json.encode("utf-8")) > SIZE_BUDGET_BYTES:
        raise BudgetError("слим-JSON превышает бюджет 300 КБ")
```

### Барьер рантайм-загрузки (презентация читает только встроенное)

```javascript
// index.html — данные берутся ТОЛЬКО из инлайн-узла, без fetch к источникам
document.addEventListener("DOMContentLoaded", () => {
  try {
    const seed = JSON.parse(document.getElementById("seed-data").textContent);
    renderScenes(seed);            // презентация лишь отображает готовые ряды
  } catch (e) {
    showDataError(e);              // деградация с сообщением, не пустой экран
  }
});
```

## Анти-паттерны

- ❌ **Рантайм-fetch данных** в `index.html` (к Kaggle/basketball-reference/любому эндпоинту) —
  нарушает конституцию и делает цифры рассинхронными с авторскими выводами.
- ❌ **Логика агрегации в JS** (пересчёт дельта-метода/средних на фронте) — утечка слоя
  данных в презентацию.
- ❌ **BI-сетка KPI-карточек / «один экран без прокрутки»** — это другой паттерн
  компоновки (insba §3), сознательно отвергнутый в пользу скроллителлинга.
- ❌ **Фронт раньше зелёных тестов пайплайна** — нарушает границу фаз (TDD).
- ❌ **Сырьё в репозитории/в файле** — встраиваем только производное (< 300 КБ); сырые
  датасеты живут в `data/` вне поставки.
```
