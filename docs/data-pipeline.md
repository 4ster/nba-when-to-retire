# Data Pipeline

Офлайн-слой данных: как из сырого датасета получается слим-JSON, встраиваемый в
`index.html`. Полный замысел — в [SPEC.md](../SPEC.md) §2; жёсткие правила —
в [RULES.md](../RULES.md).

## Принцип

Браузер потребляет **только производное**. Вся агрегация и контроль достоверности
выполняются build-time на Python; в финальный файл кладётся готовый JSON, а не сырьё.
Обновление данных = осознанная пересборка пайплайном с ревью нарратива и бампом версии,
а не рантайм-загрузка.

## Источник

- Kaggle: **`sumitrodatta/nba-aba-baa-stats`** (Basketball-Reference, лицензия CC0;
  поддерживается, обновляется). Скачивание — `task download` в каталог `data/sumitro`;
  адаптер `load_sumitrodatta` (`pipeline/datasets.py`) приводит к контракту §2.
- Используются **только сезоны NBA** (ABA/BAA отбрасываются) → охват 1952–2026.
- Источник склеивает два файла: `Advanced.csv` (`bpm` → `value`, `ts_percent`) и
  `Player Totals.csv` (`pts/trb/ast/stl/blk`, `x3p_percent`) по ключу `(season, player_id)`.
- Адаптер: фильтр лиги, дедуп обменянных игроков (сводная строка `2TM/3TM/…`), родной
  строковый `player_id` (без `factorize`), `active_next` по присутствию в следующем сезоне,
  `value` = `BPM`. Строки без `bpm` (до 1974) сохраняются с `value` = NaN, не «роняются».
- Метка данных (`data_through`) и диапазон (`season_min`/`season_max` в `meta`) выводятся
  из данных в `pipeline.build`, а не хардкодятся.

> Прежний датасет `drgilermo/nba-players-stats` заканчивался сезоном 2016–17; переход на
> поддерживаемый `sumitrodatta` расширяет охват до 2025–26. Адаптер `load_drgilermo`
> сохранён в реестре `DATASET_LOADERS` для обратной совместимости.

## Контракт данных (SPEC.md §2)

**Атом** — игрок-сезон (`player-season`):

```json
{
  "player_id": 0, "name": "", "age": 0, "season": 0,
  "era_bucket": "", "position_group": "",
  "minutes": 0, "games": 0,
  "PTS_36": 0, "REB_36": 0, "AST_36": 0, "STL_36": 0, "BLK_36": 0,
  "TS_pct": 0, "FG3_pct": 0,
  "value": 0,          // одна метрика ценности (по умолчанию BPM)
  "active_next": true  // активен ли в следующем сезоне (для survival)
}
```

**Производные агрегаты** (только они попадают в файл):

| Ключ | Что содержит |
|------|--------------|
| `aging_curve` | для `(age × position_group × era_bucket × metric)` — среднее по дельта-методу, доверительный коридор и `n` |
| `survival` | доля игроков, ещё активных, по возрасту |
| `skill_decline` | кривые по компонентам навыка, нормированные к пику = 100 % |
| `notable` | 10–20 выбранных карьер (долгожители / раннее угасание) |

**Бюджет:** производный JSON < ~300 КБ, встраивается инлайн.

## Методика и достоверность

Достоверность — ответственность слоя данных; фронт лишь отображает результат
вместе с оговорками.

- **Дельта-метод.** Кривая старения строится по изменениям год-к-году у одного
  игрока, а не сравнением разных игроков. Это нейтрализует **survivorship bias**:
  средние «по срезу возраста» завышены, потому что слабые рано уходят из лиги.
- **Скоростные метрики (per-36 / per-100).** Не суммарные за сезон — это убирает
  эффект load management и разной нагрузки.
- **Неопределённость показана.** Доверительный коридор и `n` едут вместе с кривой;
  малые выборки видны и не выдаются за факт.
- **Эпохальный конфаунд.** Разрез по эпохам (по умолчанию ≤ 1989 / 1990–2009 / 2010+)
  показывает уплощение и удлинение кривой; это оговаривается аннотацией.
- **Внеигровые данные не используются** (зарплаты, реклама, мотивация) — методическая
  оговорка показывается в интерфейсе.
- **BPM доступен с сезона 1973–74.** До этого `value` = NaN, поэтому кривая ценности
  и эпоха «≤1989» по сути охватывают 1974+ (survival/амплуа считаются по всем годам).
- **Right-censoring в `notable`.** Игроки, чей последний сезон совпадает с последним
  сезоном датасета (ещё активны на момент снимка), исключаются из «рано угасших» —
  иначе обрезанная данными карьера ложно выглядела бы ранним угасанием.
- **`skill_decline` — срезовый.** Кривые угасания навыков (US-3) считаются как среднее
  по возрасту, нормированное к пику = 100 %: они показывают относительный *порядок* и
  *тайминг* угасания, где важна форма, а не абсолютный уровень. Строгий дельта-метод
  применяется к headline-метрике `value` (US-1/aging_curve). Это осознанный компромисс
  (см. оговорку в `pipeline/transform/skill_decline.py`).

## Дефолты открытых вопросов (SPEC.md §7)

Зафиксированы в [PROMPT.md](../PROMPT.md) до фазы реализации:

- метрика ценности `value` = **BPM**;
- границы эпох = **≤ 1989 / 1990–2009 / 2010+**;
- порог включения сезона = **≥ 1000 минут** (фильтр шума).

## Пересборка

```bash
task download  # data/sumitro ← sumitrodatta/nba-aba-baa-stats (kaggle CLI + токен)
task data      # пайплайн → data/aging.json + проверка бюджета
task build     # data + встраивание в index.html + валидация
task verify    # браузерная проверка (jsdom): подзаголовок-диапазон + модалка/a11y
```

Тесты пайплайна (`task test`) покрывают корректность дельта-метода, нормализацию
per-36, обработку survivorship bias, устойчивость адаптера к грязным данным (NaN-амплуа,
строковый `player_id`, обменянные), соответствие схеме и бюджет размера — и должны быть
зелёными до начала работы над фронтом. `task verify` (jsdom + d3) исполняет `index.html`
на встроенных данных и проверяет подзаголовок-диапазон, доступность модалки и отсутствие
ошибок в консоли.
